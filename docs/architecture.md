# 架构与后续路线

## 设计原则

1. **失败关闭**：白名单为空、权限缺失、微信未运行、聊天名不确定时，宁可不回复。
2. **不注入、不改协议**：只使用 macOS Accessibility API 和键盘事件。
3. **默认草稿**：`dry_run=true` 优先于所有自动发送配置。
4. **可审计**：每个决策都有事件日志；默认不记录消息正文。
5. **低频、可停止**：硬上限、随机延迟、随机跳过、活跃时段和 Ctrl+C 总开关。

## 一次回复的状态机

```text
IDLE
  │ 发现新消息
  ▼
DEBOUNCE（等待 1.5s，确认对方没有继续发）
  │
  ▼
CHECK
  ├─ 白名单不通过 → SKIP
  ├─ 非活跃时段   → SKIP
  ├─ 频率超限     → SKIP
  ├─ 命中退出词   → DISABLE_CHAT
  └─ 通过
  ▼
GENERATE（调用模型）
  │
  ├─ 失败 → LOG_ERROR → IDLE
  ▼
REVIEW
  ├─ dry_run/draft → 打印草稿 → IDLE
  └─ auto
  ▼
PRE_SEND（再次确认聊天名、延迟、总开关）
  │
  ├─ 聊天已切换 → ABORT
  ▼
SEND（unicode 键盘事件 + Enter）
  │
  ▼
LOG → COOLDOWN → IDLE
```

## 关键实现点

### 读取

- 通过 `AXFocusedWindow` / `AXWindows` 找到微信主窗口。
- 聊天名优先取窗口标题；微信 Mac 常在输入框 `AXTitle` 里暴露联系人名。
- 消息列表优先找 `AXList`（标题为 `Messages` / `消息`），找不到时在右栏找 `AXScrollArea`/`AXList`。
- 每行取文本最长的 `AXStaticText` / `AXTextArea`；用 `AXDescription` 的 sent/received 前缀判断方向，失败时用气泡 X 坐标相对窗口中线判断。

### 去重

- 启动时把当前所有消息记为基线，不回历史消息。
- 每轮比较“上一轮文本数组”和“当前文本数组”：如果当前是上一轮的追加，取新增尾部；否则用最后一条消息的索引做回退。
- 同文本重复消息可能被合并；这是 MVP 的已知限制。

### 发送

- 激活微信，聚焦最大 `AXTextArea`（排除搜索框）。
- `Cmd+A` + Delete 清空输入框。
- 每个字符用 `CGEvent.keyboardSetUnicodeString` 发送，随机 50–200ms；偶尔插入思考停顿。
- Enter 发送。
- 发送前再次读取聊天名，与生成时不一致就放弃，降低串发风险。

## 后续路线

### P1：可用性

- 菜单栏 App：开始/暂停、当前聊天、今日回复数、最近一条草稿。
- 审批队列：`draft` 模式在菜单栏显示草稿，点“发送”才发。
- 更稳的消息去重：消息时间戳、引用、发送者名称。
- 配置文件热加载和错误提示。

### P2：多聊天

- 扫描会话列表未读红点，逐个打开、读取、回复。
- 每个联系人独立的人设、频率和开关。
- 群聊 @ 检测与白名单。
- 图片/语音/文件：先只做“转人工”，不做自动理解。

### P3：跨平台

- Windows adapter：基于 `pywechat` 的 UI Automation 接口。
- Android adapter：通知监听 + 无障碍发送（风险更高，需单独评估）。
- 官方通道 adapter：企业微信/公众号客服 API，作为合规主路线。

### P4：产品化

- 本地加密配置和密钥管理。
- 审计日志轮转、敏感信息脱敏。
- 失败重试、健康检查、崩溃恢复。
- 多账号隔离和权限控制。

## 不做的事

- 不注入 DLL、不修改微信客户端、不解密本地数据库。
- 不做群发、加好友、拉群、营销、刷屏。
- 不提供“防封/解封”能力，也不承诺账号安全。
- 不绕过验证码、设备验证或风控。
